\section{Project development}

This section describes the decisions taken during the development of
the project, according to the defined methodology. In this
chapter, the focus is on how the requirements were translated into the
structure of the tool: how the exploration was divided into two
levels, how the different parts are connected, and the scope that
guided the implementation.

The contribution of the thesis is the Talos tool, a Python tool for
hierarchical design space exploration of DNN accelerators. Talos is
intended as an architectural exploration tool: its purpose is to
compare accelerator alternatives for a workload and a set of design
constraints, first at an abstract architectural level and later using
characterized hardware IP blocks.

\subsection{Tool Overview}
Talos is programmed in Python. The idea behind the software design is
to make Talos easy to work on and modifiable without having to have
broad knowledge about the full implementation. This is important
because the tool is intended to be extended with new evaluation
models, optimization objectives, workloads, IP libraries and technological nodes.

The complete set of workload, IP-pool, and characterization
requirements used by Talos is summarized in
Appendix~\ref{app:talos_requirements}.

The intended state of Talos is that a user can provide a DNN
workload, a set of optimization objectives and constraints, and an IP
library, and obtain a traceable set of feasible architectural
alternatives. The tool is therefore designed to support architectural
decisions and comparisons, rather than to hide the exploration
process behind a single generated design.

Talos is composed of two different stages, or levels. The first level
is the Architectural Exploration. This level reduces the design space
by evaluating candidates at an architectural level, without stopping
to consider the possible IPs that could be used.

The second level is the IP-Based Hardware Evaluation. This step
evaluates the candidates selected by the previous level taking into
account the different IPs available.

The intended output is a set of candidate architectures with specific
IP choices, comparable metrics, and the mapping generated by ZigZag
for each selected architecture. Each candidate is represented
internally as an implemented accelerator composed of selected
hardware IP blocks.

The adopted flow can be summarized as follows:

\begin{enumerate}
\item A genome describes an accelerator candidate at an architectural
level.
\item The genome is decoded into an internal architecture
configuration.
\item This configuration is translated into a ZigZag-compatible
accelerator description.
\item ZigZag is used to evaluate the candidate in terms of energy,
latency, and area-related cost.
\item The architectural candidate is converted into an abstract
accelerator representation.
\item The second level selects compatible hardware IP blocks for the
abstract components.
\item The implemented accelerator is evaluated with a workload-aware
PPA model and checked against the user constraints.
\end{enumerate}

This structure reflects the main idea of the project: keeping
architectural exploration separated from hardware IP instantiation
while maintaining a path between both stages.

\subsection{Abstract Architecture Representation}
\label{subsec:abstract_representation}
In order to evaluate the different architectures, an abstract
representation that does not contain specific IPs is needed. Since
ZigZag is used in the first level, the decision was to keep this
representation close to ZigZag's hardware model.

This thesis will not go in depth about all the technical details of
their work, but a brief overview is useful to understand how Talos
represents the accelerator before moving to the IP-based evaluation
stage.

In Talos, this abstract representation appears at two different
points. First, in Level 1, an architecture is represented through a
compact genome and then decoded into a configuration that can be
exported to ZigZag. Second, when moving to Level 2, the same
candidate is translated into an internal
\texttt{AbstractAccelerator}. This object contains abstract
components such as the PE array, register files, and global buffer,
but it does not yet select concrete IP implementations.

This separation is important because the first level only needs to
know what the architecture looks like, according to the structure of the DNN algorithm to be implemented, while the second level needs
to know which hardware blocks could implement it.

\subsubsection{Hardware architecture representation in ZigZag}

ZigZag models the hardware architecture of a DNN accelerator using a
hierarchical representation that starts from the smallest compute
primitive and progressively builds the full accelerator. At the
lowest level, the \textit{operational unit} represents the basic
compute element, typically a multiplier, and is characterized by
attributes such as energy and area. Multiple operational units are
then organized into an \textit{operational array}, whose dimensions
define the available spatial parallelism.

The memory system is described through \textit{memory instances},
each one parameterized by capacity, read and write bandwidth, access
cost, area, and number of ports. These memory instances are connected
into a \textit{memory hierarchy}, which captures both storage
properties and the connectivity between memory levels and the
operational array. A relevant concept in this representation is that
of \textit{memory operands}, which decouples the hardware memory
organization from the algorithmic tensors and later links them
through the mapping specification.

ZigZag also models how memories are spatially distributed with
respect to the compute array by means of the
\texttt{served\_dimensions} attribute. This allows the framework to
represent different organizations, from private memories attached to
each operational unit to shared buffers serving one or more array
dimensions. In addition, the hierarchy explicitly models the allowed
data movements between adjacent levels, including transfers from
higher to lower levels and vice versa.

Finally, the combination of the operational array and the memory
hierarchy forms a \textit{core}, and this core is wrapped into the
top-level \textit{accelerator} object. This representation is
especially relevant because it provides an explicit and structured
description of the compute resources, memory organization, and
communication patterns of the accelerator, which are key aspects
during design space exploration and mapping evaluation.

The generated ZigZag accelerator follows a simple and fixed memory
structure. It contains a PE array, one register file for input
activations, one register file for weights, one register file for
outputs and partial sums, a shared global buffer, and an external
DRAM level.

The operand links used by Talos are:

\begin{itemize}
\item input activations are mapped to \texttt{I1};
\item weights are mapped to \texttt{I2};
\item outputs are mapped to \texttt{O}.
\end{itemize}

The external DRAM is kept in the ZigZag description because it is
needed to model off-chip traffic. However, it is not treated as part
of the accelerator area. In the current model, the DRAM has zero area
and a fixed bandwidth. This decision avoids letting the optimizer
increase off-chip bandwidth without modeling the physical cost of
the external memory interface.

\subsection{Level 1: Architectural Exploration}
\label{subsec:genome}
The first level of Talos performs architectural exploration. Its
objective is to generate and evaluate accelerator candidates without
selecting concrete hardware IP blocks yet.

The architecture is encoded as a discrete genome. Each gene is an
index into a catalog of possible values. This representation was
selected because it is simple, compatible with evolutionary
optimization, and avoids generating arbitrary values that do not
correspond to the current design space.

The current Level 1 genome contains seven genes, shown in
Table~\ref{tab:level1_genome}.
\begin{table}[h]
\centering
\begin{tabular}{ll}
\hline
Gene & Meaning \\
\hline
\texttt{pe\_x\_code} & PE array size in the first dimension \\
\texttt{pe\_y\_code} & PE array size in the second dimension \\
\texttt{rf\_size\_code} & Per-PE local storage capacity \\
\texttt{rf\_bw\_code} & Per-PE local storage bandwidth \\
\texttt{gb\_size\_code} & Global buffer capacity \\
\texttt{gb\_bw\_code} & Global buffer bandwidth \\
\texttt{gb\_served\_dims\_code} & PE-array dimensions served by the global buffer \\
\hline
\end{tabular}
\caption{Current Level 1 genome used by Talos.}
\label{tab:level1_genome}
\end{table}

The DRAM bandwidth is not present in the genome because it is treated
as a fixed platform parameter rather than an accelerator design
variable. If the IP pool contains a DRAM characterization, Talos uses
its bandwidth. Otherwise, the tool creates a fixed 512-bit platform
proxy.

After decoding the genome, Talos builds an architecture
configuration. This configuration is then used to generate the
accelerator description consumed by ZigZag. ZigZag evaluates the
mapping of the workload and provides the latency and dynamic energy
information used by Talos. The area objective is evaluated separately
using a Level 1 area calibration\footnote{calibration is the process of adjusting and tuning abstract software simulation models to match the physical measurements of real silicon or the high-fidelity golden data from low-level reference tools} derived from the characterized IP
pool.

Before starting the Level 1 exploration, Talos calibrates its energy
model with CACTI. The technology node is not fixed in the tool. It is
read from the \texttt{technology\_nm} field of the selected IP pool,
so the calibration uses the same technology as the hardware blocks
used later in the flow. CACTI is executed once before the optimization
workers and characterizes every register-file and global-buffer
capacity and bandwidth combination available in the Level 1 genome.
The obtained read and write costs are then included in the accelerator
description evaluated by ZigZag.

CACTI provides the memory access costs, but the Level 1 model also
requires values for the MAC operation, register file, and external
DRAM. To keep these values coherent, Talos uses the approximate
relative costs reported for 16-bit operations in Eyeriss
\cite{eyeriss} for 65 nm technologies:

\[
E_{\mathrm{MAC}} : E_{\mathrm{RF}} : E_{\mathrm{GB}} :
E_{\mathrm{DRAM}} = 1 : 1 : 6 : 200.
\]

These ratios are used as the default calibration for 65~nm. Although
CACTI uses the technology node declared by the IP pool, the relative
ratios are not adapted automatically. The calibration code is designed
so that these values can be customized when another technology or
energy model is used.

A 128 KiB global buffer with a 16-bit word is characterized with CACTI
and used as the reference for this ratio. Its average read and write
energy defines the global buffer cost, from which the base MAC,
register file, and DRAM costs are obtained. Each explored global
buffer and register file uses its own CACTI read and write values,
while the external DRAM cost is derived from the reference ratio and
scaled according to its access width. In this way, the Level 1 energy
model depends on both the selected technology and the architecture
being evaluated.

The first level also includes an objective adapter. This component
allows the same raw evaluation result to be exposed as different
optimization objectives, such as latency, energy, area, energy-delay
product, energy-area product, or area-latency product. This avoids
hard-coding a single objective into the evaluator and makes the
optimization process easier to extend.

In addition to the dynamic energy estimated through ZigZag, Talos adds
an idle energy estimation for the parts of the accelerator that are
not represented by the access-based model. The objective is not to
produce a detailed circuit-level power estimation at this stage, but
to prevent architectures with large amounts of unused hardware from
being considered free.

For the processing elements, Talos estimates the number of idle
PE-cycles from the latency and MAC count reported for every layer. If
an architecture contains $N_{\mathrm{PE}}$ processing elements, the
idle PE-cycles for a layer are approximated as

\[
C_{\mathrm{PE,idle}} =
\max(0,
N_{\mathrm{PE}} C_{\mathrm{layer}} -
N_{\mathrm{MAC}}).
\]

An idle energy per PE and cycle is then derived from the calibrated
MAC energy. The current model uses a configurable ratio between both
values. This introduces a penalty for architectures that contain more
compute resources than the workload mapping can effectively use.

The memory model also includes static contributions. CACTI provides
the standby leakage power of the register files and global buffers.
This power is accumulated during the complete execution time of the
workload. An additional clock-idle term is used as a simple model for
the cost of keeping the memory structures active even when they are
not performing an access. External DRAM idle power is treated in a
similar way and is accumulated during the execution time returned by
ZigZag.

Therefore, the Level 1 energy can be expressed conceptually as

\[
E_{\mathrm{L1}} =
E_{\mathrm{ZigZag}} +
E_{\mathrm{PE,idle}} +
E_{\mathrm{memory,standby}} +
E_{\mathrm{memory,clock-idle}} +
E_{\mathrm{DRAM,idle}}.
\]

This remains an architectural estimation. Its purpose is to provide a
fast and coherent comparison between candidates before selecting
specific hardware implementations in Level 2.

Area follows a different approach. Before Level 1 starts, Talos
builds an area calibration from the characterized IP pool. For each
register-file configuration, the tool searches for the minimum-area
compatible PE and RF combination. For every global-buffer
configuration, it similarly obtains the minimum-area compatible
memory IP. The Level 1 area is then estimated as

\[
A_{\mathrm{L1}} =
N_{\mathrm{PE}} A_{\mathrm{PE+RF,min}} +
N_{\mathrm{GB}} A_{\mathrm{GB,min}}.
\]

The number of global-buffer instances depends on the dimensions served
by the buffer. If a PE already contains one or more register files,
their area is not counted again. The resulting value should therefore
be interpreted as a pool-dependent lower bound for the architecture,
while the concrete IP combinations are explored later in Level 2.

\subsection{IP representation and hardware pool}
\label{subsec:ip_pool}
The second level of Talos requires a representation of the available
hardware blocks. For that reason, an IP pool was implemented.

Each IP block represents a possible hardware component that can be
selected to implement part of the accelerator. The current IP
representation contains the following information:

\begin{itemize}
\item IP identifier and type;
\item area;
\item delay and maximum operating frequency;
\item throughput;
\item optional capacity and bandwidth;
\item an idle and active power;
\item the operating point associated with the power characterization,
including frequency, voltage, temperature, and process corner;
\item optional metadata describing properties required by the
workload-aware model, such as MACs per cycle or memory accesses per
cycle;
\item optional information describing register files already included
inside a PE.
\end{itemize}

Not every field has the same meaning for every IP type. For example,
memory IPs use capacity, bandwidth, and accesses per cycle to determine
whether they can sustain the memory activity required by the mapping.
PEs can provide information such as the number of MAC operations that
can be performed per cycle. These values are later used by Level 2 to
check whether a selected physical implementation can sustain the
workload mapping obtained in Level 1.

The IP type is used to match hardware blocks with abstract
accelerator components. For example, a register file component must
be matched with a compatible memory IP, and a PE array component must
be matched with a compatible compute IP.

Capacity and bandwidth are optional fields because not all IP types
require them in the same way. When an abstract component defines one
of these requirements, Talos only considers IPs that provide at least
the required capacity and bandwidth.

The IP pool is loaded from a structured description file (YAML format). This makes
it possible to modify the set of available IPs without changing the
code. The intended use is to populate this pool with values obtained
from a coherent characterization flow, such as synthesis, memory
compilers, or other estimation tools. The description also defines one
technology node for the complete pool. Talos uses this value to
parameterize the CACTI calibration performed before Level 1, keeping
both exploration levels aligned with the same technology.

A physical IP may also cover more than one abstract component. For
example, a PE can declare that one or more register-file roles are
already included in its implementation. Talos keeps those register
files visible as abstract components for compatibility and workload
activity, but avoids counting their physical implementation twice.

During the early stages of development, synthetic characterization
values were used only to implement and validate the exploration flow.
Once the flow was stable, the IP pool used for the final evaluation
was populated with real characterization values. The resulting pools
are reproduced in Appendix~\ref{app:ip_pools}, which also includes an
annotated example of one IP entry.

\subsection{Level 2: IP-Based Hardware Evaluation}
The second level evaluates an architectural candidate using the
available hardware IP pool. The input to this level is not the
original genome, but an abstract accelerator generated from the Level
1 architecture.

This abstract accelerator is composed of several abstract components.
In the current implementation, these components usually include:

\begin{itemize}
\item the PE array;
\item one register file for input activations;
\item one register file for weights;
\item one register file for outputs and partial sums;
\item one shared global buffer.
\end{itemize}

The external DRAM is not explored as a Level 2 accelerator component
and therefore does not introduce an additional gene or contribute to
the on-chip area. However, a platform DRAM model, characterized when
provided and synthetic otherwise, is preserved as part of the platform
description because its bandwidth, idle power, and active power are
required for the workload-aware evaluation. This keeps the DRAM fixed
across the IP exploration while still accounting for the off-chip
traffic produced by the mapping.

\subsubsection{Level 2 genome and decoding}
The Level 2 genome is generated dynamically from the abstract
accelerator and the IP pool. Instead of having a fixed number of
genes, each gene corresponds to one abstract component. The value of
each gene selects one compatible IP implementation for that component,
that is, an IP of the matching type that satisfies the capacity and
bandwidth requirements defined by the component.

This design allows the second level to adapt to different accelerator
candidates. If the abstract accelerator changes, the Level 2 genome
changes with it. This is useful because the number and type of
components may evolve as the architectural representation becomes
richer.

The genome also takes into account dependencies between components.
When a selected PE already contains one or more register files, the
corresponding register-file genes are fixed by that PE instead of
being explored as independent physical choices. Both runners respect
this dependency, although each one enforces it in a different way, as
described later.

Once a Level 2 genome is decoded, Talos builds an implemented
accelerator. This implemented accelerator contains the selected IP
block for each abstract component and is the input to the Level 2
evaluator.

\subsubsection{Workload-aware evaluation}
Every implemented accelerator is evaluated with the same Level 2
evaluator, independently of the runner that generated it. Therefore,
area, workload energy, power, performance, and physical timing have
the same meaning independently of the exploration strategy. The
evaluator computes the physical metrics and checks whether the
candidate satisfies the user constraints.

Area is accumulated across the selected components, taking into
account the number of instances. Delay is approximated using the
maximum delay among the selected blocks, inference throughput using the minimum
throughput, and the implementation frequency using the lowest maximum
frequency of its components.

For workload-aware energy and power, Talos reuses the mapping
selected by ZigZag. For each layer, it considers its execution time,
the number of active PEs, and the accesses to the register files and
global buffer. These values are combined with the idle and active
power characterization of each selected IP. Dynamic DRAM access
energy is also included, although DRAM remains outside the on-chip
area and IP selection. All selected IPs use a common characterization
frequency and compatible voltage, temperature, and process corner so
that the comparison remains coherent.

A relevant decision in the Level 2 evaluation is that the workload
mapping is not generated again for every IP combination. Together with
the selected Level 1 architecture, Talos preserves the mapping
information obtained from ZigZag. For every layer, this activity
profile contains its latency in cycles, number of MAC operations,
number of spatially used PEs, and accesses to the different memory
levels.

Level 2 uses this information to determine whether a concrete
implementation can sustain the mapping selected in Level 1. For the
PE array, the required MAC operations per cycle are compared with the
number of active PE instances and the characterized
\texttt{macs\_per\_cycle} of the selected PE. For memories, the
accesses reported by ZigZag are converted into an average access rate
and compared with the bandwidth and access capability of the selected
memory IP. If an implementation cannot sustain the original mapping,
it is rejected.

This also defines how workload performance is calculated. The number
of cycles for each layer is kept from the ZigZag mapping and the total
number of cycles per inference is

\[
C_{\mathrm{inference}} =
\sum_l C_l.
\]

All the selected IP characterizations must correspond to a compatible
operating point. The workload execution time is evaluated at their
common reference frequency:

\[
T_{\mathrm{inference}} =
\frac{C_{\mathrm{inference}}}
     {f_{\mathrm{ref}}}.
\]

The resulting inference throughput is therefore

\[
Throughput_{\mathrm{workload}} =
\frac{1}{T_{\mathrm{inference}}}.
\]

The maximum frequency of the selected IPs is treated separately from
this workload performance. The physical maximum frequency of an
implementation is determined by the lowest maximum frequency among
its physical components. It is used to verify that the implementation
can operate at the required point and to report the available timing
margin, but Talos does not automatically execute a candidate at its
maximum possible frequency.

Energy is evaluated using the same workload activity profile. Each IP
contains an idle and active power characterization. For the PE array,
the power of a layer depends on the number of PEs used by the ZigZag
mapping:

\[
P_{\mathrm{PE}} =
N_{\mathrm{active}} P_{\mathrm{active}} +
(N_{\mathrm{PE}}-N_{\mathrm{active}})
P_{\mathrm{idle}}.
\]

Memory activity is estimated from the number of accesses required by
the mapping. For a memory component, its utilization is approximated
from the accesses performed during the layer, the number of memory
instances, and their characterized accesses per cycle. Its power is
then interpolated between the idle and active characterization:

\[
P_{\mathrm{memory}} =
N_{\mathrm{instances}}
\left(
P_{\mathrm{idle}} +
u(P_{\mathrm{active}}-P_{\mathrm{idle}})
\right).
\]

The same approach is applied to the external DRAM. Once the power of
all components has been obtained, the energy of each layer is
calculated from its execution time. The total energy per inference is

\[
E_{\mathrm{inference}} =
\sum_l P_l T_l,
\]

and the average workload power is obtained as

\[
P_{\mathrm{average}} =
\frac{E_{\mathrm{inference}}}
     {T_{\mathrm{inference}}}.
\]

In this way, Level 2 does not replace the workload analysis performed
in Level 1. Instead, it uses the mapping produced there as the
workload requirement and evaluates whether different physical IP
combinations can implement it, and what their resulting area, energy,
power, and timing characteristics are.

\subsubsection{Feasibility and ranking}
Candidates that cannot implement the architecture, cannot sustain the
mapping obtained in Level 1, or violate the user constraints are
discarded. The remaining candidates form the feasible Level 2 design
space, and both runners report only feasible implementations.

When only one optimization objective is selected, the feasible
implementations are simply ordered by that objective. When several
objectives are used, Talos computes the logarithmic deviation of each
minimization objective from its ideal value:

\[
r_i(x) = \ln\left(\frac{f_i(x)}{f_i^{\min}}\right).
\]

Talos then calculates the balanced score using an augmented
Tchebycheff formulation:

\[
S(x) = 100 \left[\max_i r_i(x) + 0.05 \sum_i r_i(x)\right].
\]

This score gives priority to the worst relative deviation from the
ideal value, while the sum is a secondary term that distinguishes
solutions with the same worst deviation. The balanced score is only
used to rank feasible implementations after the exploration has
finished. It does not remove candidates during the exploration and it
does not replace the individual objective values, which are also
preserved in the output.

The ideal value $f_i^{\min}$ depends on the set of solutions over
which it is computed. In the full flow, Talos recalculates the score
using one common ideal over all feasible solutions of the
architectures being compared, whichever runner produced them. This
global score is used to compare architectures.

\subsubsection{Level 2 runners}
There are two Level 2 runners: the exhaustive runner and the genetic
runner. Both share the genome, the evaluator, and the feasibility
criteria described above; they differ in how the Level 2 design space
is explored and how the resulting alternatives are ranked. Since Level
1 greatly reduces the exploration space, a genetic approach to explore
the remaining solutions may not be the most suitable option if this
remaining space is too small. For this case in particular, an
exhaustive runner was added.

\paragraph{Exhaustive runner}
The exhaustive runner was added for cases where the remaining Level 2
design space is small enough to evaluate all the possible IP
combinations. In these cases, using a genetic algorithm can add
unnecessary complexity and does not guarantee that every feasible
implementation is evaluated.

The runner works on the same Level 2 genome described above. Each IP
combination corresponds to one genome, so the number of possible
combinations is the number of distinct genomes. The runner first
calculates this number and checks it against a configurable maximum.
This prevents exhaustive exploration from being used when the
remaining IP design space becomes too large. If the number of
combinations is acceptable, every possible genome is decoded and
evaluated sequentially. Component dependencies are handled during the
enumeration, for each PE candidate, only the register-file values
consistent with that PE are generated, so combinations that would
count an included register file twice are never produced.

After the evaluation, the feasible implementations are ranked as
described above, by the selected objective when there is only one and
by the balanced score otherwise. The ideal used for this score is
local to the architecture being explored, so this local score must
not be compared directly with the score of another architecture; the
full flow recomputes the global score for that purpose.

This strategy provides complete coverage of the remaining IP
combinations and does not introduce stochastic sampling into the
physical selection. The genetic runner is kept as an alternative for
cases where the number of possible implementations makes exhaustive
evaluation impractical.

\paragraph{Genetic runner}
The genetic runner explores the same Level 2 genome with NSGA-II,
delegated to pymoo as in Level 1. The population size and the number
of generations are configurable. The genome is kept integer during the
search: the initial population is sampled as random integers, and the
crossover and mutation operators are followed by a repair step that
rounds each gene to a valid IP index and applies the component
dependencies, fixing the register-file genes covered by the selected
PE. Duplicated individuals are eliminated from the population.

The selected objectives are used directly as the NSGA-II objectives,
and the user constraints are passed to the algorithm as constraint
values, so infeasible candidates are penalized during the search
instead of being filtered only at the end. Candidates that cannot be
decoded or evaluated receive infinite objective values. The evaluation
of the individuals of each generation is parallelized over the worker
pool, as described in the parallel execution model.

The output of the genetic runner is the final non-dominated set.
Solutions that are infeasible or that select the same set of IPs are
removed, and the remaining implementations are ordered by their
objective values. The genetic runner does not compute a local balanced
score; its solutions only receive the global score computed by the
full flow. Unlike the exhaustive runner, it explores only part of the
design space, so it is intended for cases where the number of
compatible IP combinations exceeds the exhaustive limit.

\subsection{Optimization Objective Interface}
The original objective of this part of the tool was to provide a
modular fitness framework. In the current version, this idea is
implemented as an objective interface that separates evaluation from
objective selection.

The evaluator produces the raw metrics of each candidate. The
optimization configuration selects which of these metrics are
objectives. For example, one experiment may optimize latency and
energy, while another may optimize area and energy-delay product.
When several objectives are selected, the balanced or global score is
used afterwards to select one representative solution; it is not an
additional evaluator metric or optimization objective.

In Level 1, the available objectives include:

\begin{itemize}
\item latency;
\item energy;
\item area;
\item energy-delay product;
\item energy-area product;
\item area-latency product.
\end{itemize}

The standard complete flow uses energy, latency, and area together as
the default screening objectives. This selection belongs to the code
that invokes Level~1 and can be changed when defining another
exploration flow.

In Level~2, the main objectives include accelerator area, energy per
inference, average workload power, and workload latency. Physical delay
and inverse local-IP throughput are also preserved as additional
information. These values can be used by custom objectives or
alternative selection heuristics when required.

A cache mechanism is also included so that the same candidate does
not need to be evaluated multiple times when several objectives are
requested from the same result. This is especially useful when the
evaluation step is expensive in memory and time.

\subsection{Parallel Execution Model}

Talos parallelizes with processes rather than threads, because the
expensive work is the ZigZag evaluation. The number of processes is
set with the \texttt{--workers} option. Each worker has its own
evaluator and working directory, so the temporary files of different
candidates do not collide.

In Level~1, the population is passed to pymoo and pymoo evaluates each
individual in parallel on the worker pool: the genome is decoded,
ZigZag is run, and latency, energy, area, and constraint values are
returned. The genetic operators run in the main process, so each
generation is a synchronization point and the concurrency is bounded
by the population size. The energy and area calibrations are computed
once before the search and shared with the workers. The activity
profiles of the architectures selected for Level~2 are computed the
same way, one architecture per worker.

Level~2 processes the architectures received from Level~1 one at a
time. For each of them, the NSGA-II search is also delegated to pymoo,
which evaluates the individuals, in this case physical IP combinations,
in parallel with the same number of workers. The exhaustive strategy
evaluates the combinations sequentially, since its evaluation is
analytical and cheap.

Scaling is not linear with the worker count: process start-up, data
serialization, the per-generation barrier, and the variance in
evaluation time between candidates introduce overhead and load
imbalance, and each worker keeps its own copy of the workload and
evaluator in memory.

\subsection{Design Flow}
The current Talos flow starts with the Level 1 architectural genome.
NSGA-II proposes a candidate, then this genome is decoded into an 
architecture configuration and
exported to ZigZag.

ZigZag, plus the estimated values calculated for the idle
energy and the area, are used as fitness function.
It evaluates the candidate architecture and
returns the architectural metrics used by the optimizer.

After this, the Level~1 Pareto candidates are passed to Level~2. If
necessary, the set is completed with distinct feasible candidates
from the final NSGA-II population until the configured maximum number
of architectures is reached. The importer converts each architecture
into an abstract accelerator representation. This representation is
then compared against the IP pool to find compatible implementations
for each component.

Once the compatible IPs for the abstract architecture are known,
Talos can continue Level 2 using either NSGA-II or exhaustive
exploration. Both strategies evaluate each physical implementation
using the same workload-aware PPA model and the same user constraints.
The difference between them is how the Level 2 design space is
explored and how the resulting alternatives are selected or ranked.

The exhaustive strategy evaluates all compatible IP combinations, up
to a configurable maximum, and ranks the feasible implementations
after the evaluation. NSGA-II explores only part of the design space
and uses the selected objectives during the evolutionary search to
obtain a set of non-dominated alternatives, that is, solutions in
which no objective can be improved without worsening at least one of
the others.

In both cases, the workload activity profile obtained from ZigZag in
Level 1 is passed together with the abstract architecture. Therefore,
Level 2 explores different physical implementations while preserving
the mapping and workload behavior selected during the architectural
exploration.

The Level 2 genome is created from those compatibility lists. Each
candidate genome selects one IP block per abstract component. The
selected IPs are used to build an implemented accelerator, and the
Level 2 evaluator computes its physical and workload-aware values.

The complete flow can therefore be seen as a hierarchical exploration:

\begin{enumerate}
\item Level 1 explores architectural candidates.
\item ZigZag evaluates the mapping and memory behavior of those
candidates.
\item Selected candidates are converted into abstract accelerator
components.
\item Level 2 explores possible IP implementations.
\item A workload-aware PPA model evaluates the implemented candidate.
\item User constraints discard architectures that are not feasible.
\item The feasible alternatives, their metrics, and the mapping
generated by ZigZag for each selected architecture are exported for
comparison.
\item The ultimate mathematical output of NSGA-II is a Pareto front.
\end{enumerate}

Level 1 uses NSGA-II through \texttt{pymoo} and a fixed-length
architectural genome. Level 2 uses a dynamic IP-selection genome and
can use either NSGA-II or exhaustive enumeration. Exhaustive
exploration is useful when the compatible IP pool is small, while
NSGA-II preserves the same flow when the number of combinations
becomes too large. The output is a set of feasible alternatives,
including non-dominated candidates, together with their generated
mappings, rather than a single architecture selected by the tool.

\subsection{Challenges and Problems Encountered}
One of the main challenges was keeping the meaning of the metrics
coherent between both levels. Level 1 evaluates an abstract
architecture with ZigZag, while Level 2 evaluates concrete IP choices.
When the available IP combinations are introduced, an architecture
that appears less promising at the abstract level may produce a better
physical implementation, while a well-ranked abstract architecture
may offer less favorable IP combinations. For this reason, the
connection between levels was designed to preserve several candidate
architectures instead of passing only one apparent optimum.

Another problem was the distinction between energy and power.
In an early version of the flow, ZigZag energy was used as a proxy
for a power-oriented objective. This produced misleading
comparisons because a large architecture may consume less
energy by finishing earlier while still requiring more average
power. The decision was to keep energy and power as different
quantities and to make the Level 2 model workload-aware,
using the execution time and activity of each layer.

Frequency also required special attention. The maximum frequency
of an IP indicates whether it can operate at a given point,
but it is not automatically the frequency at which its power
was characterized. Combining power values from one frequency
with execution time calculated at another produced inconsistent
energy estimations. Talos therefore evaluates workload time at
the common reference frequency of the selected IP characterizations
and uses maximum frequency as a feasibility condition.

The treatment of DRAM exposed a similar modeling issue.
Allowing the optimizer to change external bandwidth without
assigning a physical cost created an unrealistic path to lower
latency. Fixing DRAM bandwidth as a platform parameter avoided this
problem. Later, the dynamic energy associated with off-chip accesses
also had to be propagated from the ZigZag mapping, because ignoring
it favored small on-chip architectures with high external traffic.

The optimization algorithms introduced practical problems
as well. Although the Level 1 genome is discrete, generic
genetic operators can produce floating-point individuals
that decode into repeated architectures and reduce population
diversity. The genome operators were therefore kept integer
throughout the search. In Level 2, NSGA-II could miss feasible
combinations when constraints were strict, even when the small
IP pool allowed all combinations to be checked. An exhaustive
strategy was added for this case, leaving NSGA-II for larger pools
where enumeration is no longer practical.

Finally, the accuracy of the exploration depends on the quality of
the external models. ZigZag does not always provide the required
area information, automatic memory characterization is
not equally portable in every environment, and a complete real
IP library was not available during the early stages of development.
Talos keeps the source of the estimates explicit: synthetic values
were used while developing the flow, while the final evaluation
used the pool obtained from real characterization.

\subsection{Validation of the Design Decisions}
The validation focuses on functional correctness and integration
between modules. The goal is not to claim final physical accuracy,
but to verify that the adopted structure works as an architectural
exploration tool.

The implemented tests cover several parts of the flow:

\begin{itemize}
\item validation of IP block definitions;
\item loading of IP pools from YAML files;
\item compatibility checks between abstract components and IP blocks;
\item rejection of invalid candidates when no compatible IP is
available;
\item (optional) generation and decoding of Level 2 genomes;
\item construction of implemented accelerators;
\item computation of area, delay, throughput, workload energy, and
average power;
\item application of area, power, latency, and frequency constraints;
\item consistency between characterization frequency, workload time,
energy, and power;
\item conversion from Level 1 architectures to Level 2 abstract
accelerators.
\end{itemize}

In addition to unit tests, smoke tests are used to verify that the
modules can be connected in practice. One smoke test creates an
architecture from the Level 1 representation, converts it into an
abstract accelerator, loads an example IP pool, generates the
corresponding Level 2 genome, and evaluates the resulting
implementation.

These tests check that Talos can represent, transform, and evaluate
accelerator candidates through both levels. They also check an
important modeling decision: the DRAM is preserved in the ZigZag
architecture for off-chip traffic modeling, but it is not imported
as an IP block in Level 2.

\subsection{Summary of the Chapter}

This chapter presented the development of Talos and the main design
decisions adopted to implement the proposed hierarchical exploration
methodology. In particular, it described the separation between
architectural exploration and physical IP selection, the
representations used to connect both levels, the evaluation models,
and the optimization mechanisms used throughout the flow.

Milestone~\ref{milestone:m3} was addressed through the characterized
IP representation and hardware pool. Physical components are described
using the implementation and operating information required by the
Level~2 PPA model, including area, timing, power, capacity, bandwidth,
and workload-related capabilities when applicable. Compatibility
between an abstract architecture and the available hardware is
expressed through component requirements rather than RTL details.
Consequently, different physical implementations can be evaluated
while keeping the architectural representation independent of a
particular RTL implementation or IP library.

Milestone~\ref{milestone:m4} was fulfilled by keeping evaluation,
optimization, workload description, hardware characterization, and
exploration strategy as separate parts of the framework. Raw
evaluation metrics are separated from the objectives selected by the
optimizer, while workloads, constraints, IP pools, and objective
combinations can be modified without redesigning the complete flow.
Level~2 can additionally use either exhaustive enumeration or NSGA-II
while sharing the same representation and evaluation model. This
modularity also allows new characterization models and objective
functions to be incorporated without changing the overall
hierarchical methodology.

The resulting implementation therefore provides the complete
infrastructure required to move from workload-driven architectural
exploration to the comparison of feasible physical implementations
while maintaining the separation between both abstraction levels.
The remaining milestone, Milestone~\ref{milestone:m5}, concerns the
experimental validation of this methodology using representative DNN
workloads and characterized hardware implementations, and is addressed
in the following evaluation chapter.
